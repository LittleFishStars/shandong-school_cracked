# 打包与发布

本项目的发布件是**单文件可执行程序**：Linux 一个 ELF，Windows 一个 exe。同一份程序既是
图形界面（双击）也是命令行工具（带参数），不需要目标机器装 Python。

## 一、产物长什么样

```
dist/
├── shandong-school_cracked-<版本>-linux-x86_64              # Linux 单文件（约 25 MB）
├── shandong-school_cracked-<版本>-linux-x86_64.zip          # 带 README.txt 与 icon.ico 的发布包
├── shandong-school_cracked-<版本>-windows-x64.exe           # Windows 单文件
├── shandong-school_cracked-<版本>-windows-x64.exe.zip
└── SHA256SUMS                            # 校验和
```

命名规则 `shandong-school_cracked-<版本>-<系统>-<架构>[.exe]`，版本号取自 `shandong-school_cracked/__init__.py` 的
`__version__`，所以**发版只改那一个值**。

## 二、本地构建

前置：Python 3.10+、`pip install pyinstaller`。本机（Arch）。

```bash
cd shandong-school_cracked
.venv/bin/pip install -i https://pypi.tuna.tsinghua.edu.cn/simple pyinstaller

.venv/bin/python scripts/build_bin.py            # 单文件
.venv/bin/python scripts/build_bin.py --zip      # 再压一份发布包
.venv/bin/python scripts/build_bin.py --onedir   # 多文件目录，排错用
```

脚本干的事：生成 `packaging/version_info.txt`（Windows 文件属性）→ 调
`packaging/shandong-school_cracked.spec` → 产物改名 → 跑 `--version` 和 `info` 冒烟 → 打印 SHA256。

**不要交叉编译**：Linux 上编不出 exe，Windows 的产物由 CI 出。

## 三、Windows / Linux 双平台自动构建

`.github/workflows/build-release.yml`：

| 触发 | 行为 |
|---|---|
| push tag `v*` | 两个平台各构建一次，然后创建（或更新）同名 GitHub Release，附件是两个单文件 + 两个 zip + `SHA256SUMS` |
| 手动 Run workflow | 只构建，产物在 Actions 页面的 Artifacts 里 |

发布一个新版本：

```bash
# 1. 改 shandong-school_cracked/__init__.py 里的 __version__
# 2. 提交并打 tag
git tag v<版本>
git push origin main --tags
# 3. 等 Actions 绿了，Release 自动出现
```

矩阵里 Linux 用 `ubuntu-22.04`（glibc 2.35），比 `ubuntu-latest` 的兼容面更宽；
Windows 用 `windows-latest`。Windows 那台会额外装 `pywebview`——**只有装了它，exe 才是
原生窗口**；没装则自动降级成本地 HTTP + 浏览器，功能一样。

## 四、打包时踩过的坑（都已修在代码里）

1. **静态资源路径**：`shandong-school_cracked/gui.py` 原来是
   `WEB_DIR = Path(__file__).resolve().parent.parent / "web"`。单文件模式下 `__file__`
   在 `sys._MEIPASS` 临时目录里，`parent.parent` 已经不是仓库根了，改成
   `_resource_dir()`：`sys.frozen` 时取 `sys._MEIPASS`，否则取仓库根。
2. **`check` 子命令**：`shandong-school_cracked/cli.py` 原来用 `subprocess.run([sys.executable, script])`
   跑 `scripts/selfcheck.py` / `scripts/webcheck.py`；打包后 `sys.executable` 就是程序
   自己，会无限重启。现在两个脚本被当作数据文件塞进包里，打包版用 `runpy` 在**同一进程**
   里执行（`_run_script_inproc`），源码模式行为不变。
3. **数据文件**：`web/`（含 `vendor/leaflet`）和两个自检脚本由 spec 的 `datas` 带入，
   目标是包内 `web/` 与 `scripts/`。
4. **入口脚本**：PyInstaller 把入口当顶层 `__main__` 跑，`python -m shandong_school_cracked` 的相对导入会
   炸，所以单独有 `packaging/launcher.py` 做绝对导入。
5. **pywebview 是运行期动态导入**，静态分析看不到，spec 里用
   `collect_submodules` + `collect_data_files` 显式收集。它**只在 Windows 构建时收集**
   （Linux 的 pywebview 后端会把整套 GTK/gi/gdk-pixbuf/图标主题拖进来，实测 +95 MB），
   所以 Linux 发布件固定走「本地 HTTP + 浏览器」，Windows 是原生窗口。
6. **瘦身**：`tkinter / unittest / PyQt* / numpy / pandas / matplotlib / gi / gevent`
   和重复的 `cryptography` 后端（`ciphers.py` 优先用已捆绑的 pycryptodome）都被排除，
   体积从 114 MB 降到 **24.8 MB**。

## 五、图标

`packaging/icon.png`（512×512）与 `packaging/icon.ico`（16–256 多尺寸）由
`packaging/make_icon.py` 用 Pillow 确定性绘制（渐变底 + 白色路线 + 起终点节点），
要改图标就改这个脚本再跑一遍：

```bash
.venv/bin/python packaging/make_icon.py
```

## 六、常见问题

- **首次启动慢 1–2 秒**：单文件模式要先把自己解压到临时目录，正常。
- **Windows Defender 报毒**：PyInstaller 打包的未签名 exe 常见误报，加白即可；
  要根治得买代码签名证书，在 CI 里签名后再上传。
- **Linux 提示 `GLIBC_2.3x not found`**：构建机的 glibc 比目标机新。用更老的发行版
  （CI 用的 22.04）重新构建，或在目标机用源码跑。
- **没有图形界面（服务器）**：`shandong-school_cracked run -d 2000 --mode mock` 这类纯命令行用法不需要
  任何 GUI 依赖。
