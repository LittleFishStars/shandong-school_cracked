## 一、为什么必须单独验这一步

`report/23-阳光跑上传接口二次核对.md` 以及 16–22 的每一条结论，判据都是 jadx 产出的 Java 源码。jadx 在三种情况下会**静默给出错误但看起来合理的接口**：

1. **漏注解**：注解写在方法参数的 `parameter_annotations` 里，jadx 偶尔丢 `@Field`/`@Body`，于是「表单接口」被看成「JSON 接口」；
2. **常量内联**：`@Field(FreeRunActivity.y)` 到底是 `targetDistance` 还是 `targetCalories`，jadx 只给常量引用名，给错一个字，整条报文就错；
3. **整类失败**：类只输出 `JADX ERROR` 注释，方法体为空，而文件仍然存在。

这三种都不会抛异常，只能靠**另一条独立判据**对冲。本次选的是 `dexdump`：它直接读 dex 的 `annotation_item`/`encoded_value`，不经过任何「重建源码」的过程，与 jadx 属于完全不同的实现路径。

## 二、方法

```bash
# 1) 16 个脱壳 dex 全量反汇编（含注解段），缓存为文本
for f in work/APP_ALL4/classes_*.dex; do
  dexdump -a -d "$f" > tmp/$(basename "$f" .dex).dexdump.txt
done      # 共 1.8 GB 文本

# 2) dex 侧：按 `Class descriptor` 定位，向上回溯本类的 `Class #N annotations:` 段，
#    解析方法级 annotation_item（http/POST、http/FormUrlEncoded、http/Headers）
#    与 parameter_annotations（http/Field、http/FieldMap、http/Body、http/Header）
python3 tmp/check_all_api.py        # 全量清单
python3 tmp/verify_api_methods.py   # 六维逐方法比对
python3 tmp/check_bean_annotations.py  # bean 的 @JSONType/@JSONField 比对
```

比对维度（每一项都必须相等）：

| # | 维度 | dex 来源 | jadx 来源 |
| --- | --- | --- | --- |
| 1 | HTTP 方法 + 路径 | `http/POST` / `http/GET` 的 `value` | `@POST("…")` / `@GET("…")` |
| 2 | 是否表单 | `http/FormUrlEncoded` 是否存在 | `@FormUrlEncoded` |
| 3 | 参数注解种类 | `parameter_annotations` 的 `http/Field`/`FieldMap`/`Body`/`Header`/`Query` | 参数上的同名注解 |
| 4 | 参数注解值（表单名） | `http/Field` 的 `value` | `@Field("…")`，**常量引用需还原成字面量** |
| 5 | 参数顺序与类型 | `proto` 类型列表 | 方法签名 |
| 6 | 返回值泛型 | 方法原型 + `annotation/Signature` | `Observable<BaseEntity<T>>` 一类 |
| 7 | `@Headers` 值集合 | `http/Headers.value` 数组 | `@Headers({…})` |

> 关键工程点：第 4 项的比较**必须在常量还原之后**做。直接比 `@Field(FreeRunActivity.y)` 与 `@Field("targetDistance")` 会得到 100% 假的「不一致」。还原表由 `tmp/build_consts.py` 从 dex 的静态字段初值建立（11,826 条）。

## 五、发现的三个「看起来像错、其实没错」的陷阱

### 5.1 常量内联：注解里的名字不是报文里发的名字

jadx 把 `@Field` 的值渲染成常量引用，必须在 11,826 条常量表里还原。上传/结算链路上的关键几条：

| jadx 里的写法 | 真实字面量 | 影响 |
| --- | --- | --- |
| `@Field(FreeRunActivity.y)` | `targetDistance` | 开跑/查询的目标距离字段名 |
| `@Field(ReadyActivity.t)` | `useCreditSword` | 是否使用学分剑 |
| `@Header(UserTrackConstant.SIGN)` | `sign` | 轨迹上传的签名头（`km7.j()`） |
| `@Field(AliyunLogCommon.TERMINAL_TYPE)` | `phone` | 登录相关终端类型 |
| `@Field(UserConstants.CHAT_PARAMS.l)` | `metaverseTeamCode` | 聊天参数（与跑步无关） |
| `@Field(yj7.g.WORKS_NO)` | `worksNo` | 作业号 |

这正是报告 16/18/23 里反复强调「`FreeRunActivity.y = "targetDistance"`」的原因：**任何只读 jadx 源码、不做常量还原的核对，都可能把字段名判错而毫无察觉。**

### 5.2 `IRunApi` 是 11 个方法，不是 12 个

dex 里 `Lcom/huachenjie/run/api/IRunApi;` 为 `PUBLIC INTERFACE ABSTRACT`，虚方法恰 11 个（`a`–`k`），jadx 文件里的 `@POST` 计数同为 11。此前口头的「12 个」是把 `ISunshineApi` 里的某个方法算进来的笔误，以本报告为准。

### 5.3 返回类型全为 `Observable`，不代表没有协程接口

`IRunApi` 11 个方法全部返回 `Lrx/Observable`；而 `ISunshineApi` 大量方法返回 `Object` + 末位 `Continuation`（Kotlin suspend，retrofit 2.6+ 的 suspend 支持）。比对时若把 `Continuation` 参数当成普通参数，会出现「参数个数差 1」的假差异——脚本里已显式跳过。
