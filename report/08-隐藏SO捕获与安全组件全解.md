## 一、突破：mmap/mprotect 钓鱼法

### 1.1 此前失败的原因

report/06 记录了 `liby.so` 的三层隐藏（找不到模块名 / maps 无路径 / ELF 头被抹），当时的所有定位手段都失败。

### 1.2 关键洞察（来自公开资料）

看雪文章[《Frida 企业级加固对抗实战：通过 mmap/mprotect 钓出壳隐藏的真实 SO》](https://bbs.kanxue.com/thread-290647-1.htm) 指出：

> 壳为了隐藏真实业务 SO，会**绕开系统 linker 私自加载**（避免被 linker 记录到已加载模块链表中），但它**绝对无法绕过 mmap 函数**！这是内核级限制。
>
> **关键特征**：隐藏 SO 完成内存映射（mmap）后，一定会紧跟一次 `mprotect` 调用，且权限设为 **RX（可读+可执行）**——这是筛选目标、定位隐藏 SO 的核心标识。

### 1.3 实现要点（踩过的坑）

| 尝试 | 结果 | 教训 |
|---|---|---|
| hook `mmap` + `mprotect`，宿主再 dump | ❌ 全部读空 | 宿主往返需数秒，壳已自毁/卸载 |
| 宿主持有 STOP 窗口内 dd | ❌ 区间已消失 | 同上 |
| **在 `mprotect` 的 `onLeave` 里立即进程内读取** | ✅ **成功** | ★ 必须**同一调用栈内**完成 |

**最终方案**：

```javascript
Interceptor.attach(mprotectAddr, {
  onEnter: function (args) {
    this.addr = args[0];
    this.len  = args[1].toInt32();
    this.prot = args[2].toInt32();
  },
  onLeave: function (retval) {
    // PROT_READ(1) | PROT_EXEC(4) == 5
    if (this.prot === 5 && this.len >= 32*1024 && this.len <= 8*1024*1024) {
      grab(this.addr, this.len, 'mprotect→RX');   // ★ 立即进程内 dump
    }
  }
});
```

## 七、方法论总结（可复用）

### 7.1 隐藏 SO 定位流程

```
① hook mmap      → 记录匿名大块分配
② hook mprotect  → ★ 捕获 prot==RX(5) 且大小合理的调用
③ 在 mprotect.onLeave 中**立即进程内读取**（关键！宿主持有 STOP 窗口会失败）
④ 分块 send（>48MB 时分片，Frida 消息上限）
⑤ 落盘后先算熵 + 找 ELF 头 + 搜密码学常量做定性
```

### 7.2 关键教训

| # | 坑 | 解法 |
|---|---|---|
| 1 | 宿主 dump 全部读空 | **进程内**在 mprotect 回调里立即读 |
| 2 | 抓到 32MB jit-cache 干扰 | 按大小过滤（≤8MB） |
| 3 | 抓到全零预分配页 | dump 后算熵，熵=0 排除 |
| 4 | ELF 头位置非 0 且字段非法 | 不能当 ELF 解析，直接做字符串/常量分析 |
| 5 | 壳自毁导致候选区间消失 | 不加 sleep，捕获即读 |

### 7.3 定性速查

| 观察 | 结论 |
|---|---|
| 大量 `Build.*` + su 路径 | 反 Root/反模拟器组件 |
| `inotify IN_ACCESS` | 防 dump 监控 |
| `signatureAlgorithm`/`signerInfo`/`APK Sig Block 42` | PKCS#7 签名 + 防重打包 |
| `android_create_namespace`/`ldinit`/`libldutils` | 自定义 linker |
| `interpreter_wrap_int64_t` | 自研字节码解释器（VMP/Java2C） |
| `/proc/%d/mem` + `pwrite64` | 可读写任意进程内存 |
