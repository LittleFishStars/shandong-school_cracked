## 三、★★ 重要发现：`sign` header 的实际生效范围

### 3.1 四组对照实验（`auth/loginCheck`）

| 场景 | 响应 |
|---|---|
| ① 正确签名（我们的算法） | `HTTP 200 {"code":0,"message":"成功",...}` |
| ② 故意错误签名（108 个 `A`） | `HTTP 200 {"code":0,"message":"成功",...}` |
| ③ 完全不带 `sign` header | `HTTP 200 {"code":0,"message":"成功",...}` |
| ④ `sign` 为空串 | `HTTP 200 {"code":0,"message":"成功",...}` |

**⇒ 登录前接口（`auth/*`、`captcha/*`）不校验 `sign`。**

### 3.2 端点存在性对照

| 路径 | 响应 |
|---|---|
| `auth/loginCheck`（存在） | `200 {"code":0,...}` |
| `auth/thisDoesNotExist`（不存在） | `404 {"code":1516,"message":"请登录后操作！"}` |
| `syncTime`（需登录） | `404 {"code":1516,"message":"请登录后操作！"}` |

**⇒ 服务端对"未知路径"与"未登录"都返回 `1516`**（统一的不泄露路由信息策略）。

### 3.3 与 report/07 的印证

report/07 曾从 smali 读出：
> **仅 `run-front/run/uploadRunRecord` 接口带 `@Header("sign")`**

本次服务端实验**完全印证**：
- 登录/验证码接口**不校验**签名
- 签名只在**轨迹上传**等业务接口生效（需登录态才能测到）

**⇒ `sign` 是「轨迹防篡改」机制，而非全局请求签名。**


```
     → {"code":0,"data":{"phone":"<AES 加密>","registerType":0}}
```

## 七、签名算法的最终定位（汇总 report/13 + 本报告）

| 层次 | 结论 | 证据 |
|---|---|---|
| **算法** | `Base64(AES-256-CBC(T(SHA256_hex(json))))` | report/13 端到端 5/5 |
| **变换 T** | `s[-8:] + s[8:-8] + s[:8]` | 逐字节核对 |
| **密钥** | `09L8MJRMJKXW8TPF ‖ 0x00×16`（生产） | 用它能解出有效 PKCS#7 + 可打印 hex |
| **IV** | `01234ABCDEF56789` | 同字段加密 |
| **生效范围** | **仅业务接口**（轨迹上传等），登录前接口不校验 | ★ **本报告 §3 服务端四组对照** |
| **与 Java 层关系** | 同一 IV；生产 signKey 来自 native 侧（report/06 黑盒所得） | |

## 八、方法论（本轮新增 2 条，累计 18 条）

17. **服务端可做「零成本对照实验」**：
    对同一接口发送「正确签名 / 错误签名 / 无签名 / 空签名」四组请求，
    比较响应差异 → 即可判定该接口是否校验签名、以及校验的严格程度。
    比纯静态分析快得多，且结论更硬。

18. **服务端的「回显」是最好的算法验证器**：
    `loginCheck` 返回的 `phone` 是 AES 加密结果，
    与本地 `encrypt_field("13800138000")` **逐字节相同** ——
    这种「服务端用同一算法重算并回显」的场景，
    等于让服务端免费为我们做了一次端到端验证。
