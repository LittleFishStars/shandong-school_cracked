## 1. 现象

用户实走（真实登录、真实围栏）2122 米 / 2526 步 / 5 个打卡点，全程 40+ 次上传均 `code=0`，

## 2. 已定位并修复的两个真实缺陷

### 2.1 步频/配速段 `index` 每次上传都从 0 重编号（`aa67975`）

- 原版 `IntervalStep.id` / `IntervalPace.id` 是 Room 自增主键（`@JSONField(name="index")`），
  全局唯一；服务端按 `(runRecordCode, index)` upsert。
- sdlab 旧实现 `protocol.build_step_list()` / `build_pace_list()` 用 `enumerate` 从头编号，
  而跑步中**每 60 秒传一次步频、每 50 米传一次配速** → 每批都覆盖上一批，结算时服务端只剩最后一批段。
- 修复：直接使用 `IntervalStep.step_index` / `IntervalPace.pace_index`，与库表一致。

### 2.2 `uploadRunRecord` 把 `indexList` 当请求内下标（`aa67975`）

- 原版 `ApiDataComponent.java:102-106`：拿服务端返回的 `indexList` 直接更新 DAO —— 它是**点的 index**。
- sdlab 旧实现用 `pts[j]`（请求内下标）回查 → 标错对象，287 个点全部停在 `UPLOADING(2)`，
  日志"轨迹上传完成：0/277 点"；服务端返回的 432…447 正是点 index（本地 161..447）。
- 修复：以 `wanted = {p.lat_lng_index}` 与 `indexList` 求交集再标记。

### 2.3 结算步数与步频段不同源（`a9af342`）

- 原版 `totalStep` 与段 `endStep` 同取 `L0()`（`DataComponent.java:1185-1200`）。
- sdlab `summary()` 取 sensor 快照 `st.steps`，与最后一段 `endStep` 差 3 步（2526 vs 2529）。
- 修复：`total_step` 取 `self.total_steps`（段末 `endStep`）。

> 以上三处都会被服务端用作一致性校验，是**必须修**的；但修完后重放该 run 仍然 1112。

## 4. 为什么判定是服务端侧

1. 报文逐字段对齐原版后仍 1112，最小报文（只 4 个字段）也 1112 —— 说明与业务字段无关。
2. 服务端已接收全部 287 个点（`indexList` 完整回显 1..287 或 161..447），仍 1112 —— 不是点缺失。
3. 同一套代码在 mock 环境完整跑通并结算（`unittest` 208 项、`webcheck` 59 项全过）。
4. `1112 = 网络可能异常，请稍后再试或联系客服` 是服务端未捕获异常的统一文案；
   客户端把请求发全了，异常发生在服务端处理该 `runRecordCode` 的内部。

> 最可能的内因（无法从客户端证实）：首次结算时（`aa67975` 之前）步频段被后批覆盖、
> 点全部停在 `UPLOADING`，服务端当时已把该 run 的部分中间态写坏，之后任何结算请求都在同一处抛异常。

- **该账号被锁**：只要服务端还认为这条 run "未完成"，任何新跑步都会被 `2070` 拒。
- 处置顺序建议：
  1. 用**手机原版 App** 打开 → 出现"您有一个未完成的跑步记录" → 点"放弃"，看是否也报错。
     - 手机同样报错 → 服务端数据坏，需客服/等定时清理；
     - 手机能成功 → 说明还有报文差异，请抓包对比（这是唯一能继续定位的路径）。

     现象"结束跑步一直提示网络可能异常(1112)，且无法开始新跑步(2070)"。
