# 19 · 跑步流程一致性核对（阳光跑）

> 范围：桌面版（sdlab）复刻的是阳光跑部分，本报告核对**跑步流程本身**——开跑 → 定位采集 → 有效性判定 → 增量上传 → 打卡 → 结算 → 暂停/续跑——与原版 APK（`com.huachenjie.shandong_school` v8.7.7 / versionCode 26101017）的一致性。
> 通信层（头、签名、加密、字段名）的差异已在报告 18 处理，本报告只覆盖流程与判定口径。

## 0 · 结论速览

原版跑步主链路（每 3 秒一次定位回调）：

```
SunshineRunService.K(addressInfo)
  ├─ E()   状态 preStart → normal（精度 > runFilterAccuracy 或卫星数 < 4 且 amapGPSLevel==2 直接丢）
  ├─ t2()  更新当前定位（f12592a）
  ├─ x2()  遍历打卡点：setInFence(dist <= CommonConfig.validDistance)，再 z0() 顺序推进
  ├─ D()   围栏外直接 return（K1）；否则
  │    ├─ W1()  与上一有效点算线距离 → H0 过滤（D1 时用 gpsFilterAccuracy）→ 有效点入库、累加距离
  │    ├─ m0()  增量轨迹上传节拍（15s）
  │    └─ E0()  步幅段统计（每 strideStatisticsInterval 米一段；R1 计异常）
  └─ F0()  打卡（clockMode 2/3 需要按顺序；clockTime = now）
```

本次核对出 **12 项流程/判定差异**，其中 9 项已修（含 3 项会导致真实跑步被判无效或打卡不认的严重问题），2 项确认「桌面版不需要」并在文档标注，1 项（反作弊上报）确定为不实现。

| # | 问题 | 严重度 | 处置 |
|---|------|--------|------|
| 1 | 开跑响应 `targetPoints[].code` 丢失，上传打卡/结算用本地序号顶替 | **高**（服务端按 code 匹配，可能不认打卡） | 已修：存储与上传全链路带真实 code |
| 2 | `clockMode` 未解析 → 顺序打卡模式没实现 | **高**（顺序模式学校打卡全不认） | 已修：`clock_mode ∈ {2,3}` 时按 sort 顺序打卡 |
| 3 | 把开跑响应 `whiteFlag` 当成 GPS 白名单 | 高（过滤半径用错，可能整趟点被丢） | 已修：GPS 白名单实际是 `SchoolRule.gpsWhiteFlag`（D1()） |
| 4 | 跑步中每 60 秒的步频段上传未实现（`o0()`） | 中 | 已修：`step_upload_due` 消费后异步 `uploadStepsRecord` |
| 5 | 增量轨迹上传只看待传 `INIT`，漏 `FAIL` 重传 | 中 | 已修：`INIT + FAIL` 都参与门控 |
| 6 | 时间口径用四舍五入，原版是整秒截断 | 低中 | 已修：`runTime = (int) Q0()`、`duration` 也 floor |
| 7 | 结算 `pauseCount/pauseTimes` 恒 0 | 中（暂停过就对不上） | 已修：暂停/继续 + 结算上报实际值 |
| 8 | 步幅异常的本地判定未门控 `L1()`，且基准用全局均值 | 中高（普通学校也会被误判无效） | 已修：`cheatLevel 3/4` 且非白名单才判 58；基准改 `segmentStrideAvg` |
| 9 | 打卡判定节拍（每帧 vs 每定位） | 低 | 保持每帧（原版约 1Hz，行为等价，注释说明） |
| 10 | `resume` 语义：原版是 App 重启恢复会话 | — | 确认桌面版不需要，文档标注「续传 = 补上传」 |
| 11 | 结算 `cheatList`（反作弊检测结果）未实现 | 低 | 不实现：来源是端侧检测 SDK，服务端自己判 |
| 12 | 暂停期间计时/计步 | 中 | 已随 7 实现（Q0 停走，不计步不采样） |

## 2 · 差异与处置

### 2.1 开跑响应的打卡点（问题 1、2、3）

原版 `StartRunEntity.targetPoints` 带 `code`、`sort`、`nfcEnable`、`type`；`code` 是服务端主键，打卡上传与结算都原样带回。sdlab 之前只留 `lat/lng/radius_m`，上传时拿本地序号顶替 `code`。

修复：

- `sdlab/store.py`：`checkpoints` 表加 `code/sort/nfc/type`；`checkpoint_targets()` 返回真实 `code`、`sort`、`nfcEnable`。
- `sdlab/client.py`：`start_sun_run` 解析时保存 `clockMode/whiteFlag/cheatLevel` 并写 `runs` 表（新增三列）；打卡点保留 `code/sort/nfcEnable/type`。
- 顺序打卡：`Walker._check_targets` 在 `clock_mode ∈ {2,3}` 时只允许命中 `_next_target`，命中后 `+1`。

`whiteFlag` 不是 GPS 白名单：它是 `L1()` 作弊判定的白名单（`DataComponent.java:519`）。GPS 白名单是 `SchoolRule.gpsWhiteFlag`（`D1()`，`DataComponent.java:322`）。修复：

- `sdlab/protocol.py`：`RuleSet` 增加 `gps_white_flag`（解析 `gpsWhiteFlag`）。
- `sdlab/walk.py`：`w.gps_white_flag` 改从 `client.rule.gps_white_flag` 取，不再用 `run_white_flag`。

### 2.2 上传节拍（问题 4、5）

- 60 秒步频上传：`Walker` 每到 `(Q0()-1) % 60 == 0` 置 `step_upload_due`；`WalkSession._maybe_upload_steps()` 消费该标志并异步调 `client.upload_steps(run_code)`（线程名 `sdlab-step-upload`），失败保留待传。
- 增量轨迹：`_maybe_upload_points` 的门控从 `count_points(run_code, INIT) <= 0` 改为 `INIT + FAIL <= 0`，失败点会被重传。

### 2.3 时间口径（问题 6）

- `Walker` 的 `run_time = int(elapsed_sec)`（floor），不用 `round`。
- `_persist_run_summary` 的 `duration = int(duration_s)`（floor）。

### 2.4 暂停/恢复（问题 7、12）

原版 `userPause` 时 `Q0()` 停止推进，`y0()` 把 `pauseCount + 1`，`pauseState` 的 `pauseTime/savePauseTime` 累计真实暂停时长；结算 `pauseTimes = (savePauseTime + pauseTime) / 1000`。

sdlab 新增：

- `Walker.pause()/resume()`：`paused` 期间 `tick()` 直接返回，`pause_sec += dt`（虚拟时间，等价墙钟累计）；`pause_count` 只在真正在跑时自增。
- `WalkSession.pause(on)` → `App.walk_pause(on)` → `GuiBridge.walk_pause(on)`；Web GUI 的「暂停 / 继续」按钮（`btn-walk-pause`），暂停时按钮变「继续」。
- `store.runs` 加 `pause_count/pause_times_s`，`finish_run` 落库；`client.finish_run` 读这两个值填 `pauseCount/pauseTimes`（不再恒 0）。

### 2.5 步幅异常（问题 8）

原版 `W0()` 的 58 号原因由 `L1()` 门控（`cheatLevel 3/4`、异常段数超 `segmentStrideExceptionNum`、非 `whiteFlag`、非 `D1()`）；异常计数 `R1()` 的基准是**服务端下发的 `segmentStrideAvg`（厘米）**，不是全局平均步幅。

修复：

- `evaluate_run(..., cheat_level=0, white_flag=False, gps_white_flag=False)`：只有三者条件都满足才加 `INVALID_STRIDE`。
- `Walker.segment_stride_avg_cm`：由 `walk.start` 从 `client.rule.segment_stride_avg` 注入（小于 10 视作米并 ×100）；`_maybe_stride_segment` 只在 `seg_dist >= 200 且 stride_cm > 基准` 时计异常。
- `Engine._stride_exceptions`：仿真链同样改为「段步幅（常量）> 基准 且 段距离 ≥ 200」口径。

### 2.6 确认不做 / 不需要

- **`cheatList`**：来源是端侧检测 SDK（`SunshineRunService.java:600` 回填），桌面版不接检测 SDK；服务端仍会自己判定，故不上报。
- **`resume` 语义**：原版 `run/resume` 用于 App 重启后恢复跑步会话；桌面版进程内不会丢会话，现有「续传」= 补上传 + 补结算，语义不同但用途正确，已在 `docs/协议说明.md` 标注。
- **打卡判定节拍**：原版每个定位回调（约 3 秒）判一次，sdlab 每帧（0.2 秒）判一次。行为等价（同一半径、同一顺序规则），且界面需要即时反馈；保留并注释。

## 3 · 修复后的流程

```
walk.start()
  ├─ 注入 clock_mode / gps_white_flag / segment_stride_avg_cm（来自开跑响应与 SchoolRule）
  ├─ targets 按 (sort, index) 排序（顺序模式游标从这里开始）
  └─ loop:
       walker.tick(dt)
         ├─ paused → pause_sec += dt，直接返回
         ├─ 推进位置 → set_joystick / auto_route
         ├─ _check_targets()            # 顺序模式只认下一个；命中记 hit_ms
         ├─ _sample_if_due()            # 每 3 秒：围栏外丢弃；H0 过滤；落库；步幅段；配速段
         ├─ _advance_clock()            # 每秒：步频段切分、60 秒上传节拍
         └─ summary()
       _drain()                         # 打卡 → store；轨迹 → store；分段 → store
         ├─ _maybe_upload_points()      # INIT+FAIL 有待传 → 15 秒节拍 → uploadRunRecord
         └─ _maybe_upload_steps()       # step_upload_due → uploadStepsRecord
  stop() → _drain_tail → evaluate_run(cheat_level/white_flag/gps_white_flag) → finish_run
```

## 5 · 仍存疑

- `clockMode == 1` 的分支（`DataComponent.java:658` 用 `j1()/h1()` 判打卡）与顺序模式（2/3）的差异还没逐行核对，当前只实现 2/3。
- `SchoolRule.segmentStrideAvg` 的单位在真实下发里没有样本（mock 用 0.85，代码按「<10 视为米」兼容），需要抓一次真实响应确认。
- 自动暂停（`PauseTimerType.AUTO/SPEED_ERROR/FACE_RECOGNITION/NFC_CHECK`）与手动暂停共用 `pauseCount`，桌面版只实现手动暂停。
