## 二、`targetPoints` 元素：本轮发现并修复的第一处不一致

原版 `com/huachenjie/common/bean/TargetPoints.java:19`：

```java
@JSONType(includes = {"lat", "lng", "clockTime", "code", "passStatus"})
public final class TargetPoints implements Parcelable, Comparable<TargetPoints> {
```

fastjson 的 `includes` 是**白名单**：只有这 5 个键会被序列化。类里那些 `@JSONField(serialize=false)` 只是 Kotlin data class 的残留注释，真正起过滤作用的是类头这一行。

对照：

| 版本 | 发出字段 |
| --- | --- |
| 原版 | `code, lat, lng, passStatus, clockTime`（5） |
| run-lab 修复前 `protocol.build_target_points()` | 5 + **`sort`、`nfcEnable`**（7） |
| run-lab 现在 | 5（`store.checkpoint_targets()` 一直是对的） |

即：**真正上楼的两条路径（`finish_run` / `upload_checkpoints`）本来正确**，错的是 `protocol.build_target_points()` ——它被 `tests/test_protocol.py` 当参考实现断言，一旦有人拿它去替换 store 就会多报两个字段。已改成 5 字段并把断言换成白名单等值断言，防止回归。

另外，`targetPoints` 的 `lat/lng` 必须用**服务端下发的桩点坐标**（`getTargetPoints()` 从开跑响应反序列化后只改 `passStatus/clockTime`，永不改写 lat/lng），`store.checkpoint_targets()` 的注释已写明。

## 五、验证方式与输出

```
$ cd shandong-run-lab && .venv/bin/python -m unittest -q
Ran 210 tests in 22.685s
OK
```

端到端断言的技术点：

1. `upload_log` 是 `ORDER BY id DESC`，**`[0]` 才是最新一条**。曾按 `[-1]` 取到首次结算报文，误判「pois 没发出去」——这类坑写进注释。
2. `uploadRunRecord` 在 `upload_log` 里记的 `payload_json` 是 `{"count": N}` 摘要（真报文是另一份），不能用它反推元素字段；要拿 `RunLatLng.to_upload_dict()` 比对。
3. 结算报文在同一次跑步里可以出现多次（重复结算、异常结束），断言必须锁定「最新」。
