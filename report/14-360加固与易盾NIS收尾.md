## 一、360 加固保：`makekey` 的真实身份

### 1.1 起点：`makekey` 在哪个二进制里？

report/10 记录：1148KB 隐藏段（`work/hidden_so3/so_0x7ca8bda000.bin`）的
`.dynstr` 里有 `makekey`，伴随 24 个 360 相关字符串。

**本次精确核实**：

```bash
$ strings -a so_0x7ca8bda000.bin | grep -c "^makekey$"
1
$ strings -a so_0x7ca8bda000.bin | grep -iE "jiagu|qihoo|360|oset" | head
makekey
libjiagu.so
com/jiagu/sdk/%s
com/qihoo/bugreport/CrashReport
libjiagu_sdk_
/.jiagu
jiagu_vip
com.jiagu.sdk.
/libjiagu_
libjiagu.so
doSetShellState
QIHOO
jiaguVersion
com/qihoo/util/upgrade/Upgrade
360DC_DeviceId
```

**★ 关键修正**：`makekey` 位于该段的 **`.dynstr`（导入符号表）**！
它不是实现的函数名，而是**从外部库导入的符号**。

`makekey` 的字符串位置 `0x4e50` 周边全是 `dlopen` / `dlsym` / `calloc` / `getpid` /
`snprintf` / `strrchr` / `strtoul` / `atol` / `time` 等 libc 导入 —— 佐证它是导入项。

### 1.2 决定性实验：hook `dlopen` / `dlsym`（v35 / v36）

```javascript
['dlopen', 'android_dlopen_ext', 'dlsym'].forEach(nm => {
    Interceptor.attach(Module.getGlobalExportByName(nm), { onEnter: ... });
});
```

**实测输出（v35）**：

```
[dlopen] "libjiagu.so"                    ← 声称加载 360 核心
[dlsym]  "doSetShellState"                ← 声称解析加固标志 API
[android_dlopen_ext] ".../libjiagu_sdk_OSETSDKProtected.so"
[android_dlopen_ext] "/data/user/0/.../files/.motion/libxt_a64.so"
[android_dlopen_ext] ".../libNetHTProtect.so"
[android_dlopen_ext] ".../libsecsdk.so"
```

**★ 决定性证据（v36 加了 `dlsym` 返回值捕获）**：

```
[dlopen] "libjiagu.so"
[dlsym 结果] doSetShellState → 0x0        ← ★★★ 返回 NULL！
（进程模块列表中：只有 libnesec.so，没有 libjiagu.so）
（全内存搜 "makekey" / "doSetShellState" / "QIHOO" / "jiaguVersion" / "360DC_DeviceId" → 0 处）
```

**⇒ 结论**：

| 项 | 结论 |
|---|---|
| `dlopen("libjiagu.so")` | **失败**（设备上不存在该文件，全盘搜索也无） |
| `dlsym(..., "doSetShellState")` | **返回 NULL**（符号不存在） |
| 这组调用的用途 | **探测式调用** —— 检查环境是否已有 360 加固 / 是否为模拟器 |
| `makekey` 符号 | **导入符号，永不解析成功**（提供者不存在） |
| 实际加固实现 | 在 `libjiagu_sdk_OSETSDKProtected.so` 内部（熵 7.741，自解密） |

**⇒ 360 加固的"`makekey`"是一个设计上的**幌子**：
壳故意导入一个不存在的符号，既用于环境探测，也用来误导分析者。

### 1.3 排除 `.motion/libxt_a64.so`（曾是最大嫌疑）

该文件是 360 落地到 `files/.motion/` 的 290 KB 动态库，**未加密**（熵 6.002），
一度被认为就是 `libjiagu.so` 的真身。深度分析后**排除**：

```
ELF 64-bit ARM aarch64, NDK r29, BuildID=c24e681c...
节表：.text 173,384 B / .rodata 16,948 B / __lcxx_override 268 B
.dynstr 仅 94 条，关键符号：
    AMotionEvent_getEventTime      ← ★★★ Android 输入事件时间戳
    AMotionEvent_getDownTime       ← ★★★ 按下时间
    gettimeofday / pthread_cond_signal / pthread_key_create / pthread_key_delete
可见字符串 577 个，无 "jiagu" / "makekey" / "QIHOO" / "360DC" / "doSetShellState"
```

**⇒ `libxt_a64.so` 是「触摸事件注入/记录」组件**（`.motion` 目录名 = motion event），
**不是加固库**。

### 1.5 360 加固保的最终结论

| 问题 | 结论 |
|---|---|
| `makekey` 在哪？ | **不存在实体实现** —— 是导入符号，`dlopen("libjiagu.so")` 失败、`dlsym` 返回 NULL |
| `libjiagu.so`？ | 设备上不存在（全盘搜索确认） |
| 真正的加固实现在哪？ | `libjiagu_sdk_OSETSDKProtected.so`（797 KB，熵 7.741，**自解密**） |
| 运行时产物 | `.imprint`（设备指纹明文）+ 1800+ 个 128 字节槽 + `.motion/libxt_a64.so`（触摸库） |
| 对主链路的影响 | **无** —— `signRequest` 不依赖 360（见 report/13） |

**⇒ report/10 §八 第 3 项（"360 加固保载荷密钥 makekey"）正式结清：
该项是一个**设计上的误导**，实际不存在可还原的 `makekey` 实现。**

### 2.2 静态特征

```
大小   349,040 B

JNI_OnLoad   ×2  @0x2df6
Java_*       ×0      ← ★ 无任何 Java_ 导出（方法名运行时注册，同 liby.so 手法）
```

### 2.3 与主链路的关系

`libsecsdk.so` 是**易盾 NIS**（基础安全 SDK），与 `libNetHTProtect.so`（HTProtect 风控）
同属易盾体系但**职责不同**：

| 库 | 职责 | 与 signRequest 的关系 |
|---|---|---|
| `libNetHTProtect.so` | HTProtect 风控 token（`PRODUCT_ID=YD00717730319426`） | **并行路径**（report/12 已证非真实现） |
| `libsecsdk.so` | NIS 基础安全（设备指纹/环境检测） | 独立，不参与签名 |
| `liby.so` | ★ **signRequest 真实现** | **主链路**（report/12/13） |

**⇒ report/10 §八 第 4 项（"libsecsdk.so 方法级加密"）结清：
该库确认为易盾 NIS 基础安全模块，与签名算法无关；
其方法级加密与 `liby.so` 采用同样的"运行时注册 + 名称抹除"手法，
对本项目主链路（登录→阳光跑→记录→上传）**无影响**。**

## 六、方法论（本轮新增 3 条，累计 16 条）

14. **"导入符号"不等于"存在的实现"**：
    `.dynstr` 里的名字只是**引用**。看到一个诱人的符号（如 `makekey`）时，
    必须先确认它是在导出表还是导入表，再去 `dlopen`/`dlsym` 验证是否真能解析。

15. **`dlopen`/`dlsym` 的返回值是关键证据**：
    壳会用"探测式调用"（必然失败的 `dlopen`）来检测环境。
    **只看 `onEnter` 会误判**（"它加载了 libjiagu.so"）；
    **必须看 `onLeave` 的返回值**（`0x0` = 不存在）。

16. **目录名/文件名容易误导**：
    `.motion/` 曾被认为是 360 伪装，深入后发现它真的对应
    **motion event**（`AMotionEvent_getEventTime`）。
    判定组件性质要看**导入符号**与**节结构**，而不是名字。
