## 三、脱壳方案

### 3.1 三个必须跨过的坎

#### 坎 1：进程 2 秒自毁

**现象**：无论是否挂 Frida，进程都在约 2 秒后 `System.exit(0)`。

**排查过程**（全部失败）：
- 拦 libc `exit` / `_exit` / `_Exit` / `abort` / `quick_exit` → **零命中**
- 拦 `syscall` 的 `exit_group(94)` → 零命中
- 拦 `kill(self, SIGKILL)` → 零命中
- 禁用 LSPosed → 行为不变
- 追加 Magisk denylist + Shamiko → 行为不变
- 清理 `/data/local/tmp` 的脱壳器痕迹 → 行为不变

**根因**：ART 的 `System.exit` 走的是 `java.lang.System.exit → Runtime.exitInternal` 的 **Java 路径**，不经过 libc；且壳还大量使用**内联 SVC 指令**（见 [SVC 指令级系统调用保护](https://overkazaf.github.io/blogs/posts/android-svc-syscall-protection/)），进一步绕开所有 libc hook。

**解法**：在 Java 层 hook `System.exit`：

```javascript
Java.perform(function () {
  Java.use('java.lang.System').exit.implementation = function (code) {
    send('拦截 System.exit(' + code + ')');   // 不调用原实现
  };
});
```

**效果**：进程存活 **2.1s → 42s+**。

#### 坎 2：native hook 装上但永不触发

**现象**：hook 了 `OpenCommon` 却没有任何日志。

**根因**：`readelf` 给出的符号值是 **vaddr**，而 Frida 的 `Module.base` 指向**首个映射**。本机 `libart.so` 首个 LOAD 段的 `p_vaddr = 0x27000`（不是 0），导致地址整体偏移：

```
运行时地址 = Module.base + readelf_vaddr − 首个LOAD段vaddr
           = Module.base + vaddr − 0x27000
```

**验证**：修正后 `OpenCommon` 立即开始命中（捕获到 `cdex001` 与 `dex\n035` 缓冲）。

#### 坎 3：Frida 进程内读取受保护内存不可靠

**现象**：读 `DexFile` 对象得到固定值。

**分析**：壳用 `mprotect(PROT_NONE)` 撤销解密区读权限；且 Frida 的进程内读取器对这类区域表现不稳定。

**解法**：**改从内核视角读** —— hook 只负责**报告地址**，宿主用 `/proc/<pid>/mem` 读（先 `SIGSTOP`）：

```bash
su -c 'kill -STOP <pid>'
su -c 'dd if=/proc/<pid>/mem of=... bs=4096 skip=<块号> count=<页数>'
su -c 'kill -CONT <pid>'
```

**注意**：toybox `dd` 的 `skip` 是 **32 位块号**，且目标地址通常**不在页首**，因此：
- 块号 = `addr / 4096`（本机 0x7c.. 地址 ≈ 1.3e8，落在 int32 内可用）
- 页数必须把页内偏移算进去，否则**尾部被截断**：`页数 = (size + addr%4096 + 4095) / 4096`
- 读回后切掉前 `addr%4096` 字节

### 3.2 最终脱壳链

```
① Frida spawn + Java 层拦 System.exit          → 进程保活
② hook art::ClassLinker::DefineClass           → libart.so base + (0x11c7d8 − 0x27000)
   x2 = 类描述符（过滤 Lcom/huachenjie）
   x5 = const DexFile&  → 把地址报给宿主
③ 宿主 SIGSTOP，用 /proc/<pid>/mem 读该对象 512B
④ 扫描对象前 64 字节的 8 字节字段，取第一个指向 "dex\n"/"cdex" 的作为 DEX 起点
   ★ 本机 Android 9 的 art::DexFile 布局与教科书不同：
     offset 0 不是 begin_，**offset 8** 才是指向 dex 数据的指针
⑤ 读 DEX 头的 file_size(0x20) → 整块取出 → 落盘
⑥ 必要时重算 checksum(Adler-32)/signature(SHA-1)
```

## 五、请求签名与安全机制分析

### 5.1 三层安全防御体系

## 七、踩坑清单（可复用）

| # | 坑 | 表现 | 解法 |
|---|---|---|---|
| 1 | 偏移未修正 | native hook 永不触发 | `addr = base + vaddr − 0x27000` |
| 2 | Frida 17 无 Java bridge | `'Java' is not defined` | esbuild 打包 `frida-java-bridge` 注入全局 |
| 3 | esbuild 改写 `require` | 返回模块对象，`not a function` | 直接用全局 `Java` |
| 4 | `Interceptor.replace` 崩溃 | tombstone 指向 `frida-agent-64.so` | 只用 `attach` + `this.ret` |
| 5 | 拦 `pthread_exit` | 从 `noreturn` 返回是 UB | 不拦该类函数 |
| 6 | `enumerateClassLoaders` 包装器 | 拿不到 `pathList` | 先 `Java.cast(loader, BaseDexClassLoader)` |
| 7 | `DexFile.mCookie` 类型 | 按 `Long` 转换全失败 | 它是 **`long[]`**，取 `[0]` |
| 8 | 硬编码 `DexFile` 偏移 | offset 0 不是 `begin_` | 扫描对象前 64 字节找 dex magic |
| 9 | `dd` 页内偏移 | DEX 尾部被截断 | 页数计入 `addr % 4096` |
| 10 | ART quickening | checksum 校验失败 | 重算 Adler-32 / SHA-1 |
| 11 | 任何枚举 maps 的 Frida API | 进程立即退出 | 用 `/proc/pid/maps` 从外部读 |
| 12 | **类名过滤写窄** | 漏掉整个自研 SDK（`huachenjie.sdk.http`） | 同时匹配 `Lcom/huachenjie` **与** `Lhuachenjie` |
| 13 | 入口文件追加而非重建 | esbuild 报 `import` 重复，**且静默跑旧 bundle** | 每次重新生成入口（见 `build_frida_bundle.py`） |
| 14 | 只看 `classes.dex` | 漏掉 `assets/*.jar` 里的独立 DEX | 检查 `assets/*.jar`（`jy.jar`、`Z8...jar`） |
