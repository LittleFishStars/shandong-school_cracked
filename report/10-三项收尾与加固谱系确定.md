## 一、项 1：PKCS#7 的公钥来源

### 1.1 静态搜索：blob 内无证书

对 892 KB blob 全面扫描：

| 搜索项 | 结果 |
|---|---|
| DER X.509 结构（`30 82 ?? ?? 30 82`） | **0 个** |
| PEM 头（`-----BEGIN`） | **0 个** |
| Base64 证书特征（`MII`/`MIIC`/`MIID`） | **0 个** |
| RSA OID（`1.2.840.113549.1.1.1`） | **0 处** |
| ECDSA / SM2 / SM3 OID | **0 处** |
| PKCS#7 signedData OID | **0 处** |

**⇒ 证书不在 SO 里** —— 只能是运行时从外部读入。

### 1.2 APK 里的证书资产

```
assets/huachenjie.pem          5,519 B   ← TLS 证书链（3 张）
assets/nim/cacert            213,092 B   ← 网易云信 CA
assets/grs_sp.bks / hms*.bks  ——          ← 华为 BKS 信任库
META-INF/RUNNING.RSA         1,201 B     ← ★ APK v1 签名（PKCS#7）
META-INF/RUNNING.SF      1,091,788 B
META-INF/MANIFEST.MF     1,091,664 B
```

### 1.3 两类证书的用途区分（关键）

| 文件 | Subject | Issuer | 有效期 | 用途 |
|---|---|---|---|---|
| `assets/huachenjie.pem` | `CN=*.huachenjie.com` | RapidSSL → DigiCert | 2025-08-22 ~ 2026-09-04 | **TLS / SSL Pinning** |
| `META-INF/RUNNING.RSA` 内嵌 | `C=cn, ST=zhejiang, L=hangzhou` | **自身** | 2020-09-07 ~ **2120-08-14** | **APK v1 签名** |

**判据**：`RUNNING.RSA` 的证书是**自签名**（Subject == Issuer）且有效期 **100 年**（2120 年）—— 典型的**自签名调试/自用证书**，不可能是 CA 签发或 TLS 用途。

### 1.4 ★ SDK 解析器与实际结构的逐项对照

report/09 从 `FUN_0007c9f8` 反编译出的每个字符串断言，都能在 `RUNNING.RSA` 里找到对应：

| SDK 代码中的断言 | `RUNNING.RSA` ASN.1 位置 |
|---|---|
| `s_contentInfo` (0x30 SEQUENCE) | `0:d=0 SEQUENCE` |
| `s_contentType` (0x06 OID) | `pkcs7-signedData` @4 |
| `content-[optional]` (0xA0) | `15:d=1 cont [0]` |
| `s_version` (0x02 INTEGER) | `23:d=3 INTEGER :01` |
| `DigestAlgorithms` (0x31 SET OF) | `26:d=3 SET → sha256` |
| `s_contentInfo` (0x30) | `43:d=3 SEQUENCE → pkcs7-data` |
| `certificates-[optional]` (0xA0) | `56:d=3 cont [0]` |
| `tbsCertificate` (0x30) | `60:d=4 SEQUENCE` |
| `signerInfos` / `s_signerInfo` | `839:d=3 SET` / `843:d=4 SEQUENCE` |
| `digestAlgorithmId` | `911:d=5 SEQUENCE → sha256` |
| `digestEncryptionAlgorithmId` | `926:d=5 SEQUENCE → rsaEncryption` |
| `encryptedDigest` | `941:d=5 OCTET STRING`（**256 字节** = RSA-2048） |

**⇒ 结论：公钥来源 = APK 自身的 v1 签名块（`META-INF/*.RSA`）里内嵌的证书。**

SDK 用它做 **APK 自校验（防重打包）**，无需任何外部公钥 —— 这也解释了为什么 blob 里搜不到证书。

## 二、项 2：签名值的字段拼接顺序

### 2.1 方法：native 层 hook MD5 压缩函数

```
① mprotect→RX 钓到目标段（892 KB）
② 立即在 段基址 + 0xb6a04 安装 hook（偏移来自 Ghidra 分析）
③ 记录每次 MD5 压缩函数的 (state[4], data[64]) 入参
```

**首条记录即验证命中**：

```
MD5 state = 67452301 efcdab89 98badcfe 10325476     ← ★ MD5 标准初始值
data      = 30820307308201efa00302010202040cfe2b19…  ← X.509 证书 DER
                    ↑                              ↑
              SEQUENCE                  serial = 0x0CFE2B19
```

`0x0CFE2B19` **正是 `RUNNING.RSA` 里那张证书的 serial**。

### 2.2 重建被哈希的数据

拼接全部 13 个 64 字节块 → **832 字节**，其中前 **779 字节**构成完整 DER：

```
开头: 30820307308201efa00302010202040cfe2b19300d06092a864886f70d01010b
      └ SEQUENCE(0x307) └ SEQUENCE(0x1ef) └ [0] version └ INTEGER serial(0xCFE2B19)
尾部: ...（RSA 公钥模数 + 扩展 + 自签名）
```

**写出并验证成功**：

```bash
$ openssl x509 -inform DER -in work/certs/from_md5_hook.der -noout -subject -issuer -serial
subject=C=cn, ST=zhejiang, L=hangzhou
issuer =C=cn, ST=zhejiang, L=hangzhou
serial =0CFE2B19
SHA-256= 35:71:25:38:32:DC:0F:23:A4:87:18:EA:FA:E1:73:EE:9D:0F:04:E1:D3:A0:6D:34:3E:37:87:A6:C4:18:30:AD
```

### 2.3 ★ APK v1 签名的完整摘要链验证

进一步验证 SDK 校验的是**整条 APK v1 签名链**：

| 环节 | 验证 | 结果 |
|---|---|---|
| ① SF 的 `SHA-256-Digest-Manifest` == `SHA-256(MANIFEST.MF)` | `2P3nA22OK0jNOdrARa7VWSsxK3C7WlcwuoGUqdOAVKc=` | ✅ **完全匹配** |
| ② SF 各条目摘要 == `SHA-256(MF 中该条目段 + \r\n\r\n)` | 逐条比对 1,199 条 | ✅ **1199/1199 通过** |
| ③ PKCS#7 对 SF 签名（detached） | RSA-2048 + SHA-256，签名值 256 字节 | ✅ 结构完整 |
| ④ APK Sig Block 42（v2）首尾 size 一致 | 4,088 == 4,088 | ✅ |

**补充发现**：`RUNNING.SF` 含 `X-Android-APK-Signed: 2` —— 显式声明使用 **APK Signature Scheme v2**。

```
摘 要 链 全 景：
  MANIFEST.MF ──sha256──→ RUNNING.SF 的 Digest-Manifest 字段
       ↑                        ↑
   每条目 sha256            整文件 RSA 签名
       ↑                        ↑
  RUNNING.SF 条目           RUNNING.RSA（PKCS#7 + 证书）
                                ↑
                        SDK 解析并校验 ← 本次完整还原
```

### 2.4 为什么 MD5 而不是 SHA-256？

观察到的分工：

| 算法 | 用途 |
|---|---|
| **MD5** | 证书指纹 / 防篡改初筛（速度快） |
| **CityHash64** | 内存 / 字符串快速哈希（非加密用途） |
| **SHA-256** | APK 签名链的正式摘要（规范要求） |

SDK 对证书单独做 MD5，属于**自实现的附加校验**（APK 规范本身只用 SHA-256/SHA-1）。

## 七、★ 追加：`signRequest` 调用链定位（用「触发追踪法」）

### 7.1 方法

在 892 KB 段内 hook 10 个候选函数入口，然后调用 `signRequest`，观察哪些被触发：

```
[hook] PKCS7 FUN_0007c9f8
  → 触发 FUN_0009fb70
  → 触发 MD5封装 FUN_000b6950
  → 触发 MD5压缩 FUN_000b6a04   ×13 次   ← 832/64 = 13 块（与证书长度吻合）
  → 触发 MD5封装 FUN_000b6950   ×2
  → 触发 FUN_00083560
  → 触发 FUN_000a3460
═══ signRequest 结果: 82nIn4Xz+WshQAVduVf2A5xSzQRSdFC2AVzkBigf... ═══
```

**⇒ 完整调用链：`FUN_0009fb70` → MD5 ×13 → `FUN_00083560` → `FUN_000a3460`**

### 7.2 三个函数的职责（反编译确认）

#### ① `FUN_0009fb70`（6,104 B）—— 环境位图生成

引用全部国产 ROM 包名：
```
com_amigo_ / com_baidu_ / com_gionee_ / com_google_ / com_iflytek_
com_komoxo_ / com_meizu_ / com_miui_ / com_pp_assistant_ / com_android_
```
以及 **`"0011111001111111111"`**（21 位 ASCII 位图，逐位表示各项检测结果）。

#### ② `FUN_00083560`（6,500 B）—— 易盾配置读取

```c
uVar15 = FUN_000b8b3c(lVar13, "assets/nedig.properties");
if (uVar15 & 1) {
    FUN_000b8d80(lVar13, "assets/nedig.properties", &local_508);
    ...
}
```

**`nedig.properties` = 易盾（Netease Digital）配置文件** —— 引用 `META-INF` / `assets` / `nedig.properties` / `1_2_8`。

> **重要修正**：这证明 892 KB 段是**易盾的 native 组件**（与 `com.netease.nis.wrapper` 同源），而非完全"自研"。

#### ③ ★ `FUN_000a3460`（8,736 B）—— 易盾 ART 层注入引擎

```c
// ① 打开 libart.so 并取 art::Runtime 单例
uVar19  = FUN_000d8cb0("libart.so", 2);                        // dlopen
plVar16 = FUN_000d8cc0(uVar19, "_ZN3art7Runtime9instance_E");  // dlsym ← ART Runtime!
if (plVar16 != NULL) { ... }

// ② 反射改 DexPathList.dexElements（DEX 注入经典手法）
plVar20 = FUN_000d1714(*plVar15, plVar15, "dalvik/system/DexPathList$Element");

// ③ 读 Android 版本分支
auVar40 = FUN_000d1714(*plVar15, plVar15, "android/os/Build$VERSION");
auVar39 = FUN_000d3314(..., "RELEASE", "Ljava/lang/String;");

// ④ 进程替换（反调试/自毁路径）
pcVar32 = "execv";   uVar19 = 0x91d6c;    // 或
pcVar32 = "execve";  uVar19 = 0x91da8;

// ⑤ 环境位图
pcVar32 = "0011111001111111111" + 0x10;

// ⑥ Java2C 标记
FUN_0004ed04(&local_110, "163java2c0");
```

**`163java2c0`** —— **`163` = 网易**，`java2c` = Java → C，`0` = 版本号。这是**易盾 Java2C 编译产物的运行时支撑标记**。

### 7.3 关于 80 字节输出的进一步发现

MD5 一共被调用 **13 次**（`832/64 = 13`）—— 这**正是证书 DER 的块数**，说明 `signRequest` 路径里**也走了证书的 MD5**。

但 80 字节输出经检验：

| 检验 | 结果 |
|---|---|
| 字节熵 | **6.0625**（理想随机上限 = 6.0，共 70 种取值） |
| 是否含 4 个已知密钥的哈希 | ✗ 无 |
| 是否含证书的 MD5/SHA1/SHA256 | ✗ 无 |
| 是否含 `MD5(k+m)`/`HMAC-*` 等 8 种构造 | ✗ 无 |

⇒ 80 字节 = **高熵、确定性、非标准构造**。结合 §6.2 的结构切片（前 32 / 中 32 / 后 16），
最可能是 **`SM3(32) ‖ SM3(32) ‖ MD5(16)`** 或类似的自定义哈希链拼接（需在 `FUN_000a3460` 返回点 dump 中间值才能定论）。
