## 0. 一句话结论

这是一个**被网易易盾加固的 Flutter + 原生混合应用**，原生代码在加固时被抽走了
DEX 头部并通过单文件 `classes.dex`（141 MB，99.9% 是追加载荷）承载原始多 DEX 主体。
本次分析已经**证明原始 DEX 主体是明文**（`string_ids` 全量 70,145 条 100% 校验通过，
基址唯一确定为 `85,240`），因此**静态还原 Java 层代码是可行的**，只是需要重建 112 字节
DEX 头；同时应用的 TLS 校验形同虚设（信任用户 CA），动态抓包几乎零成本。

## 2. 保护与加固（本次分析的核心）

### 2.1 加固方案判定：网易易盾（NetEase NIS）

证据链：

1. Manifest 的 `application android:name` = `com.netease.nis.wrapper.MyApplication`。
2. `classes.dex` 只有 **30 个类**，全部落在 `com.netease.nis.wrapper.*` 与混淆包 `a.auu.*`。
3. `libnesec.so` / `libnesec-x86.so` / `libNetHTProtect.so` / `libne_audio.so` 存在。
4. 壳内字符串解密后得到加固版本号 **`7.6.3_936`**（`MyApplication.VER`）。

> 附带发现：`libjiagu_sdk_OSETSDKProtected.so` 内含 `libjiagu.so`、`JIAGU_ENCRYPTED_DEX_NAME`、
> `/StubApp` 等 **360 加固** 特征串，说明包内还混入了 360 加固体系的运行时库（被改名的
> `libOSETSDKProtected.so` / `liboset-pine-lib.so` / `libosetutil.so`），推测用于广告
> SDK 自身的安全模块。判定：**主加固为网易易盾，另含 360 jiagu 系运行时组件**。

### 2.2 壳层工作流（已还原）

| 类 | 职责 |
|---|---|
| `com.netease.nis.wrapper.MyApplication` | 入口 Application，`attachBaseContext`/`onCreate` 中加载并驱动壳 |
| `com.netease.nis.wrapper.MyJni` | JNI 桥（数百个 `n0xxxx` 混淆 native 方法）；从 assets 抽取并解密 `.so` |
| `com.netease.nis.wrapper.o` | `System.loadLibrary` 与 so 抽取/校验逻辑 |
| `plugin.InstrumentationProxy` | 替换 `ActivityThread.mInstrumentation` 做插件化调度 |
| `plugin.g` | 篡改 `libraryPathElements` / `nativeLibraryPathElements`（发版时不走标准 ABI 装载） |
| `ProxyComponentFactory` | 代理 `AppComponentFactory`，接管类加载器 |
| `CrashHandler` | `uploadCatchedException` / `leaveBreadcrumb` 上报 |

关键流程（脱敏后的逻辑）：

- 把 `assets` 中形如 `<载荷>.so` 的资源按 ABI 释放到应用私有目录 `/templib/`，
  比较文件后**只对前 4 字节做 `^0x37` 异或**再写盘，最后 `System.load()`；
- `ReLinker` 兜底重链（`com.netease.nis.wrapper.user.ReLinker`）；
- 用 `dalvik.system.BaseDexClassLoader` + 反射 `makePathElements` 装载解密后的 DEX；
- 通过 `assets/.nesec_patch` / `nesec_patch2` 支持运行时补丁。

### 2.3 壳字符串解密（已完成）

解密算法还原自 `a/auu/a.c(String)`：**Base64 解码 → 与循环密钥 `b"Netease"` 逐字节异或 → UTF-8**。
脚本：`scripts/yidun_strings.py`，产出 `work/yidun_decoded.txt`（223 条去重字符串）。

从中还原出的**反分析 / 风控能力清单**（原样列出，中英双份）：

| 网络/位置 | VPN、代理、抓包（嗅探）、**位置伪造**、屏幕共享 |
| 输入/操作 | **模拟点击环境** |

命中后的用户可见提示：`检测到…` 以及 `请前往官方渠道下载正版APP`。

### 2.4 `classes.dex` 结构与载荷性质（重点）

| 项目 | 值 |
|---|---|
| 文件大小 | 141,103,628 字节 |
| DEX 版本 | 035 |
| 头部声明 `file_size` | 141,103,628（**被篡改为整文件大小**） |
| string_ids / type_ids / proto_ids / field_ids / method_ids | 1,468 / 133 / 538 / 74 / 879 |
| class_defs | **30** |
| 头部声明的 data 区 | 21,556 – 79,616 |
| **追加载荷** | **141,024,012 字节（99.9%）** |

对载荷做了三项结构性取证（脚本 `scripts/scan_dex_payload.py`，产出 `work/dex_payload_scan.md`）：

1. **不是加密数据**：分块熵仅 4.2–6.6（加密数据应接近 8.0），且含 **985,017 条长度≥8 的可打印字符串**。
2. **含真实应用的 DEX 内容**：`Lcom/huachenjie/` 出现 **12,979 次**、`Lcom/kwad/` 7,668 次；
   甚至能看到 Kotlin 的 SMAP 调试信息（`+ 2 _Collections.kt\n*L\n37#1,2:57`），
   而壳自己的 `com/netease/nis/wrapper` 只出现 29 次（均在头部壳 DEX 中）。
3. **全文件只有 1 个合法 DEX magic**（偏移 0，即壳），说明**原始 DEX 的 112 字节头被破坏/加密**，
   但**节区主体仍为明文**。

进一步用「节区自证」方法定位原始 DEX（脚本 `scripts/probe_dex_sections.py`）：

```
[*] 待验证的 string_ids 数组起点: 89,340
[*] 基址扫描结果 (命中/60): [(60, 85240)]          <- 全局唯一候选
[+] string_ids 全量解析: 成功 70,145 / 失败 0 (100.00%)
[+] type_ids 起点 369,920，连续长度 = 11,330
```

**结论**：载荷中嵌入的是一份**原始 DEX（多 DEX 拼接）的明文主体**：

- 该 DEX 基址 `B = 85,240`，`string_ids` 数组位于 `89,340`，共 **70,145** 条，全部可解析；
- `type_ids` 位于 `369,920`，`type_ids_size = 11,330`；
- 被破坏的只有 **112 字节头部**（magic / checksum / signature 及各节区 size/off 字段）。

→ **静态还原路径成立**：只要按节区结构反推 `proto_ids / field_ids / method_ids / class_defs / map_off`
等字段并重建头部，即可得到可被 jadx/apktool 正常处理的 DEX。这比动态脱壳更省成本，且可复现。
（载荷共 141 MB，初步判断由多份 DEX 主体首尾相接组成，需逐个定位基址。）

## 4. 攻击面与安全配置

### 4.1 网络安全配置：信任用户 CA + 允许明文（高危）

`res/xml/network_security_config.xml`：

```xml
<network-security-config>
  <base-config cleartextTrafficPermitted="true">
    <trust-anchors>
      <certificates src="system"/>
      <certificates src="user"/>      <!-- 关键 -->
    </trust-anchors>
  </base-config>
</network-security-config>
```

- Manifest `android:usesCleartextTraffic=true`。
- **`src="user"` 使应用信任用户安装的 CA**：在 root/模拟器设备上装入抓包证书即可
  **完整解密 HTTPS**，无需 Frida 绕过 SSL Pinning。这是本样本动态分析成本极低的主因。
- 应用内另有 20+ 个 SDK 各自的 `*_network_security_config.xml`（ltmb/lywm/zj/zjadx/kcbw…），
  其中部分同样放开了明文或用户 CA，需逐个核对。

### 4.6 WebView JS 桥：`AlipayJSBridge` 无白名单校验

`assets/h5_bridge_part1.js`（3,133 B）+ `h5_bridge_part2.js`（519 B）、
`assets/render_h5_bridge.js`、`assets/workerjs_v8.js` 是**阿里 mPaaS 的 `AlipayJSBridge` 通用桥**
（part2 带中文注释，说明被 App 改写过）。part1 的核心接口：

```js
window.AlipayJSBridge.call(func, param, callback)   // func 完全由 H5 页面指定
```

**桥层不对 `func` 做白名单校验**，因此任何在 WebView 里加载的页面
（包括被 XSS 的 H5、第三方广告落地页、被中间人篡改的页面）都能调用宿主注册的全部 JSAPI。
part2 还注入了 `AlipayJSBridge.startupParams`、`window.APVIEWID` 与
`__RENDER_WORKER_IPC_MP__` MessageChannel IPC 通道。
结合 §4.1 的「信任用户 CA」配置，这一攻击面在抓包场景下可直接利用。

> 实际可调用的 JSAPI 命令集需动态 hook 枚举（静态无法穷举），已列入下一步工作。

## 9. 下一步计划（建议执行顺序）

1. **静态重建 DEX 头**（成本最低、收益最高）
   - 反推 `proto_ids/field_ids/method_ids/class_defs/map_off`，为载荷中每一份 DEX 主体重建 112 字节头；
   - 产出可用 jadx 反编译的 DEX，随后按 `com.huachenjie.*` 业务包逐一审计；
   - 脚本基线已有：`scripts/probe_dex_sections.py`。
2. **动态脱壳交叉验证**：准备一台可 root 的 Android 模拟器/真机，用 Frida 在
   `attachBaseContext` 之后 dump 内存 DEX（`frida-dexdump`），与静态还原结果比对。
3. **接口层取证**：利用信任用户 CA 的配置，抓取登录、跑步上报、成绩提交请求，
   还原签名/加密算法（重点 `local_iv` 与 `com.huachenjie.run`/`sport` 包）。
4. **无障碍套件行为取证**：审计 `com.acse.ottn.*` 与 `cn.hzjizhun.*` 的实际行为
   （是否自动点击、拉起安装、上报设备信息）。
5. **Flutter 侧**：用 Blutter 分析 `libapp.so`（Dart 3.4），还原 AI 运动考勤逻辑。
6. **风控绕过需求确认**：若后续需要真机调试，需先处理易盾的 root/Hook 检测
   （壳内检测项已全部枚举，可直接定位对应 native 函数）。
