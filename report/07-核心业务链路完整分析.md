## 八、结论与观察

### 8.1 链路完整性评价

| 环节 | 还原度 |
|---|---|
| 登录（8 种方式 + 双 token + 持久化 + 设备指纹） | **完整** |
| 网络层（5 层拦截器 + 加密 + 签名 + token 校验） | **完整** |
| 开跑（24 字段会话对象 + 精确参数映射 + 规则表） | **完整** |
| 数据记录（3 张表结构 + 状态机 + 6 个采集监听器） | **完整** |
| 数据上传（7 接口 + 聚合报文 + 断点续传） | **完整** |
| 反作弊（5 类无效原因 + 配速/步幅/距离规则） | **完整** |
| `liby.so` 内部算法 | **未攻破**（见 report/06） |

### 8.2 设计亮点

1. **三层数据落库 + 状态位续传**：`STATE_INIT/FAIL/SUCC` + `is_uploaded`，弱网下也能完整补传
2. **token 与签名强绑定**：token 放进 `hq1` 环境对象，签名时一并使用 ⇒ 换 token 即签名失效
3. **只有轨迹需要签名**：把有限的风控算力用在最有价值的数据上
4. **设备 ID 三层降级**：缓存 → ANDROID_ID → Build 指纹，规避隐私限制且稳定
5. **四类暂停独立计时**：人脸/NFC/自动/手动分开累计，避免"暂停刷时长"

### 8.3 可改进点（防御视角）

| 问题 | 影响 |
|---|---|
| AES 密钥与固定 IV 明文写在 smali | 加密形同虚设（见 report/05） |
| `accuracy`/`speed`/`satellites` 不上传 | 服务端无法独立判断 GPS 质量，只能信任客户端 |
| 本地判定 `status` 由客户端计算并上报 | 可被篡改（客户端说了算） |
| 配速/步幅阈值来自客户端下发的 `SchoolRule` | 篡改本地规则文件即可放宽判定 |
| `runScene==20` 才做人脸核验 | 其他场景无活体校验 |
