## 十一、结论与观察

### 11.1 安全设计评价

| 维度 | 评价 |
|---|---|
| **加固强度** | 高。易盾 App Packer + 自定义 linker + 内联 SVC + root/模拟器检测 |
| **签名机制** | 强。算法下沉 native，Java 层不可见，且只对核心接口（轨迹）强制 |
| **加密设计** | **中等**。AES-128-CBC **固定 IV**（`01234ABCDEF56789`）、密钥硬编码在 Java 层可读位置 —— 若密钥泄露，加密形同虚设 |
| **指纹完备性** | 较好。9 字段 + 时间偏移，能识别大部分环境伪造 |
| **反作弊纵深** | 强。客户端签名 + 动作识别 + 人脸活体 + 服务端风控四重 |

**最薄弱的环节**：AES 密钥 `F44B0282BEA83557` 与固定 IV 直接写在 Java 层（`r24` 类的 smali 里是明文 `const-string`），任何能读 DEX 的人都能拿到。而**唯一真正安全的**是 `liby.so` 里的签名算法。

### 11.2 值得注意的设计问题

1. **`Question.answers` 字段**：题目结构里含正确答案字段，需确认服务端是否在考试阶段就下发（若是，则理论考试可本地判分）。
2. **固定 IV**：`AES/CBC` 用固定 IV 会导致**相同明文产生相同密文**，可被流量分析识别（如判断两个账号密码是否相同）。
3. **加密开关默认关闭**：实测 `h33.e() == false`，且只有标注 `e:1` 的接口加密 —— 大部分流量是明文。
4. **申诉通道存在**：说明风控有误判，且官方接受人工复核。

### 11.3 未完成事项

| 项 | 原因 |
|---|---|
| `liby.so` 签名算法 | 保护等级与壳同级（符号加密、熵 6.88、无 JNI 导出），需 IDA/Ghidra 深入 |
| `encodeRun` 编码格式 | 同上 |
| 实际流量验证 | 未做抓包对比（可 hook `signRequest` 抓输入输出对） |
