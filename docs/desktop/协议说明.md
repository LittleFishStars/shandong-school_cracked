# 协议与逆向要点

> 本文记录重写这套客户端时确定下来的协议事实。所有结论都来自对 **`com.huachenjie.shandong_school` v8.7.7**
> 的静态分析与**服务端常量交叉验证**（例如字段密文逐字节一致），不是猜测。
> 常量集中放在 `shandong-school_cracked/constants.py`，任何改协议的动作只改那一个文件。

## 0. 总览

```
登录/备跑         记录（本地）                      上传（分批）                结算
loginCheck   ─┐                                    uploadRunRecord★  ─┐
滑块验证码     ├→ startSunRun_v2 → points/steps/paces → uploadStepsRecord ├→ finishSunRun_v2
loginPassword ┘   （拿记录号与打卡点）               uploadPaceRecord   ┘   （服务端复核）
                                                    uploadPassPoint
```

* 基址：`https://api.huachenjie.com/run-front`
* 鉴权：登录后服务端下发 `token` / `satoken`，此后所有业务请求放在请求头里（`Authorization` / `satoken`）。
* **只有 `run/uploadRunRecord` 需要 `sign` 签名**（`Endpoint.need_sign=True`），其余接口不校验。
* 常量版本：`APP_VERSION="8.7.7"`、`BUILD_VERSION="26101017"`、`APP_CODE="SD001"`。

## 1. 公共字段与请求头

原版把「9 指纹 + sign」放在 `ParamsInterceptor` 层，所以**所有 POST 的 body 与所有
GET 的 query 都会带上这 9 个字段**（`net.public_fields()`，值一律是字符串）：

| 字段 | 说明 |
| --- | --- |
| `modelName` / `systemVersion` / `platform` | 机型、系统版本、平台，来自设备指纹配置 |
| `appVersion` / `buildVersion` / `channel` / `appCode` | 版本与渠道 |
| `deviceId` | 设备号，**由 12 个 `Build` 字段长度拼接后取 hash 而来**（见第 4 节） |
| `timestamp` | 毫秒时间戳（本地时钟 + 服务端校准偏移），参与签名 |

### 1.1 头规则（`EncryptInterceptor` + `ParamsInterceptor` 逐行核对）

| 请求类型 | 头 | 说明 |
| --- | --- | --- |
| GET | （无自定义头） | 只把 9 指纹拼进 query；**不签名**、不带 UA/token |
| POST `@FormUrlEncoded` | `Content-Type: application/json`、`User-Agent`、`app/pv/k/e/api/v`、`Authorization`/`satoken`、`sign` | 表单体被改写成 **value 全为 String 的 JSON**；`e` 默认空串，`@Headers({"e:1"})` 才是 `"1"` |
| POST `@Body`(JSON) | `Content-Type`、`User-Agent`、`Authorization`/`satoken`、`sign` | 原样发 JSON，**不带** `app/api/v/e/pv/k` |

- `app` 恒为 `run-front`；`api`/`v` 取自 URL 的三段路径（`run-front/<api>/<v>`）。
- `Content-Type` 是 `application/json`，**没有 charset**。
- `User-Agent` = `ShanDong/<versionName> (<Build.BRAND>;Android <release>)`，品牌不是机型前缀。
- sign 覆盖「最终发出的 JSON 字符串」，所以 `net._do_post()` 的顺序是：
  字符串化 → 字段加密 → 补 9 指纹（缺才补）→ 序列化 → 签名。
- 哪些接口是表单、哪些是 `@Body`，看 `constants.Endpoint.form`；
  线缆级回归用 `scripts/audit_wire.py`。

## 2. 签名（`crypto.get_sign`）

```
sign = AES-CBC( swap_ends( sha256_hex(body_json) ) , signKey , iv )
```

* `body_json` 必须与**实际发出去的字节完全一致**（紧凑分隔符，不转义非 ASCII）——
  传 dict 时用 `json.dumps(body, separators=(",",":"), ensure_ascii=False)`。
* `swap_ends(hex64)` 把 64 个 hex 字符按 `尾 8 + 中 48 + 头 8` 重排（自逆，解密同式）。
* `signKey = 8 字节明文密钥 + 16 个 0x00`（共 24 字节，走 AES-128-CBC 时只用前 16 字节）。
  生产密钥 `SIGN_KEY_PROD`，`env ∈ {9, 11}` 时用测试密钥 `SIGN_KEY_TEST`。
* 结果 base64，长度固定 **108 字符**（`transport.post(..., need_sign=True)` 自动加）。

## 3. 字段加密与滑块

| 用途 | 算法 | 密钥 / IV |
| --- | --- | --- |
| 手机号、密码等敏感字段 | AES-128-CBC | `FIELD_KEY` = `F44B0282BEA83557` + 16×00；IV = `01234ABCDEF56789` |
| 滑块验证码坐标 | AES-128-**ECB** | `SLIDER_KEY` = `Ukp3hmSe7BmMcgbE` |
| 结算码 `runImgRecord` | `MD5(code + versionCode + versionName + KEY(env) + timestamp)`，与 native `encodeRun` 一致（`report/17`，6/6 预言机全中） | 32 位小写 hex |
| 部分 native 参数 | DES-ECB（8 组 8 字节密钥，按索引选） | `DES_KEYS` |

**`e` 请求头决定服务端是否解密请求字段**（2026-10-17 三组对照定论，它是「密码明明对却一直
`code=1604 密码不正确`」的根因）：

| 请求头 `e` | 服务端行为 |
| --- | --- |
| `0` / 空 | **不解密**请求体，字段按字面值参与业务（AES 密文被当成密码原文比对 → 必然 1604） |
| `1` | 先解密 `terminalType` / `password` / `userName` / `schoolName` / `studentNumber` 五个字段再用 |

* APK 里带 `@Headers({"e:1"})` 的 17 个端点中，登录链路上的四个是 `auth/loginCheck`、
  `auth/loginPassword`、`account/sendAuthCode`、`account/login_v3`；在 `constants.EP` 里写作
  `Endpoint(..., encrypt=True)` —— 传输层会自动把 `e` 置 1 并对 `ENCRYPT_FIELDS` 里的字段加密
  （`crypto.encrypt_body_fields()`，在原版里由 `EncryptInterceptor` 完成）。**调用方传明文即可，
  不要自己先加密**，否则会被二次加密。
* 响应侧**永远**加密，与 `e` 无关：`loginCheck` 回显的 `data.phone` 就是密文。
* 对照证据（已固化在 `scripts/realcheck.py` 第 2.5 节）：`school/firstPageSchoolList` 的
  `schoolName` 同在字段表里，`e=0 + 明文` 与 `e=1 + 密文` 返回的 5 条逐条完全一致，
  而 `e=1 + 明文` 返回的是另一组 —— 证明服务端只看 `e` 决定解不解密。

**滑块坐标伪装**（关键，服务端按伪装后的值比对）：
```
fake_x = int(raw_x - 6.5) + 16.5          # SLIDER_MARGIN=6.5, SLIDER_OFFSET=16.5
pointJson = AES-ECB(json({"x": fake_x, "y": 15.0}))   # y 固定 15.0
```

验证码流程（**已对真实服务端实测通过**，`scripts/realcheck.py` 5/5 一次挑战内过）：

```
captcha/get  {"captchaType":"blockPuzzle"}  → originalImageUrl / jigsawImageUrl / token
   ↓  下载两图，用 alpha 通道裁出真缺口形状；缺口模板画在与背景图等高的画布上，
      所以 alpha bbox 的 top 就是缺口纵坐标 → 只在 ±4 像素的行带里做灰度 SAD 匹配
   ↓
captcha/check {"captchaType":"blockPuzzle", "token": …, "pointJson": AES-ECB({"x": 缺口x + 10, "y": 15})}
```

★ **两个必坑点**（早期就是在这里绕了很久）：

1. `captcha/check` **一次性**——每调一次就消费掉该 `token`。失败重试必须重新
   `captcha/get` 换新挑战，**不能在同一个 token 上换坐标重试**（否则表现为「全 x 扫描零命中」）。
2. 明文里的 `x` 必须带 **+10** 的滑块留白补偿（`crypto.encrypt_slider_point()` 已内置），
   直接提交缺口原始像素会被判错。

密钥来源也已在反编译里定案：`JavascriptApi.java:656` 的 `V(handler, "secretKey", "Ukp3hmSe7BmMcgbE")`
即 H5 `CaptchaVerifyPage` 从原生桥拿到的就是这把固定密钥（与 `SLIDER_KEY` 同一个值）。

**交叉验证**：`crypto.encrypt_field("13800138000") == "WQZsdeHd/SBQZ8ZhmJzWhg=="`，
与服务端回显常量逐字节一致 ⇒ 纯标准库 AES 实现正确。

## 4. deviceId

App 里设备号是三层降级：能取到 `Build` 字段就按 `model/brand/manufacturer/device/product/board/
hardware/display/id/bootloader/fingerprint/radio` 十二项**长度的个位数**拼成一个串，再做 Java 风格 `hashCode`；
取不到则退回随机串。`simulator.build_device_fingerprint(cfg)` 复刻了这条逻辑，长度 16。

## 4.1 登录态持久化（token 存本地，进程退出不丢）

原版把登录态写在 SharedPreferences（token/satoken/userId/schoolCode），启动直接读，
**只有用户主动「退出登录」才清**；App 进程被杀、手机重启都不影响下次打开。

本项目对齐为本地库 `kv` 表：

| 项 | 说明 |
|---|---|
| 键 | `session`（真实服务端） / `session_mock`（Mock 模式），两套互不污染 |
| 字段 | `token`、`satoken`、`schoolCode`、`userId`、`loginAt`、`deviceId`、`userName`、`schoolName`、`studentNumber`、`avatar` |
| 写入 | 登录成功（`loginAt` 取当前时间）；`load_user()` 刷新用户信息（**不覆盖 token、不改 `loginAt`**） |
| 读取 | `ShandongClient.__init__` → `_load_session()`，恢复 token 等并置 `logged_in` |
| 校验 | `App.__init__` → `_restore_session_bg()` 后台 `load_user()`：`code=0` 补用户信息并提示「已恢复登录」；`1516` 才 `logout(remote=False)` 清本地并提示重新登录；网络异常**保留**会话 |
| 清除 | 仅 `App.logout()`（显式退出登录）→ `client.logout(remote=True)`：先 POST `account/logout`，失败也清本地 |

两个曾经的坑：

1. `App.close()` 里调了 `client.logout()`。命令行每条命令结束都会 `close()`，
   于是「登录 → 跑一次 → 会话被删」，下次必须重登。现在 `close()` 只停 Mock，
   不发登出。
2. `_save_session()` 原来整体覆盖，`load_user()` 刷新用户信息时会把 token 冲掉。
   现在与 `self.user` 合并，且 `loginAt` 只在登录动作里更新。

### 4.1.1 多账号：历史账号直接切换

- 每次登录成功把会话登记到 kv `accounts` / `accounts_mock`：按 `userId` 去重，最多 20 个，
  最近登录在前；每条含 `token`/`satoken`/`schoolCode`/`userId`/`loginName`/`loginAt`。
- 切换入口：Web 左栏「历史账号」下拉 +「使用该账号 / 移除」；CLI
  `shandong-school_cracked users`、`shandong-school_cracked users use <id>`、`shandong-school_cracked users rm <id>`。
- 切换动作：换 token → `load_user()` 刷新身份 → 清掉上一个账号的围栏/规则/打卡点缓存 →
  重拉 `common/getConfig`、学期、围栏列表。**不需要重新输密码**（等价于原版本地换一份
  SharedPreferences）；跑步进行中拒绝切换。
- token 过期（`1516`）：把该账号从历史里摘掉，并回滚到切换前的身份。
- 退出登录只清当前会话，历史账号保留（原版只有一份登录态，多账号是本项目扩展）。

## 5. 一次阳光跑

### 5.1 开跑（`run/startSunRun_v2`）

九参数，**顺序固定**（错一位服务端就当作别的字段）：

```
schoolCode, fenceCode, activityCode, lat, lng, targetDistance, useCreditSword, runPlanCode, sportType
```

九个字段里 `lat`/`lng` 是**开跑那一刻的定位**，原版取手机当前定位，服务端会拿它校对是不是在电子围栏里。
本工作台默认取围栏多边形重心（`fence_center()`），也可以**在地图上自己选一个起跑点**
（`set_start_point` → 本地库 kv `start_point`）：点到围栏外会自动吸附进围栏
（与边界留 `SNAP_MARGIN_M = 10` 米，避免 GPS 抖动被判出界），且这同一个坐标同时用作
实走轨迹的起点与路径规划的起点——三处一致，报文里报的“起点”才和轨迹对得上。

### 5.1.1 打卡点只在开跑后下发（与原版一致）

反编译 `com/huachenjie/common/bean/GeoFenceDetail.java` 可以看到：**电子围栏里只有打卡点的数量**
（`requiredPointCounts` / `optionalPointCounts` / `totalGoalCounts`），没有任何坐标；坐标在
`StartRunEntity.targetPoints` 里，而 `StartRunEntity` 是 `run/startSunRun_v2` 的响应
（`com/huachenjie/run/api/ISunshineApi.java:103`）。原版就是「围栏 → 点开始跑步（带此刻定位）→
服务端回 runRecordCode + targetPoints → 进跑步页才画打卡点 → 边跑边 `run/uploadPassPoint`」。

本工作台照此实现：

| 阶段 | `status().checkpoints` | `status().checkpoints_source` | 地图上画什么 |
| --- | --- | --- | --- |
| 拉取配置后 | `[]` | `""` | 只画围栏；打卡点一个不画 |
| 开跑后 | 服务端下发的点（同时写进本地库） | `"server"` | 打卡点编号（命中后紫转绿） |
| 服务端没下发时（仿真/异常） | 按围栏几何预估的点 | `"preview"` | 同上，但会在事件流里 warn |

* `preview_points`：拉取配置阶段按围栏几何预估的 N 个点（顶点向质心缩 0.55），**只**给
  “高级 / 调试”里的「只规划路径」当预览，不会在开跑前画到地图上；
* `walk_plan().estimated`：`true` 表示这次规划用的是预览点（还没开跑），开跑后以服务端下发为准；
* 即“打开软件就有打卡点”是不对的——旧实现把上一趟记录里的打卡点从本地库回显了出来，已删。

返回里给出记录号 `runRecordCode` 与打卡点 `targetPoints`（客户端写入本地库，作为轨迹生成的目标点）。

### 5.2 记录

| 本地表 / 报文 | 采样 | 内容 |
| --- | --- | --- |
| `points` / `pois` | 3 秒一点 | lat、lng、runTime、collectTime、state、offFenceDisM、isValid |
| `steps` / `stepList` | **20 秒一段** | startStep、endStep、startTime、endTime、step、time |
| `paces` / `paceList` | **每 50 米一段** | distance、start/endDistance、stepCount、time、pace |
| 步幅 | 同上 | `strideList` + `strideInterval` |

`stepInterval` / `paceInterval` 的默认值就来自 `com.huachenjie.common.bean.CommonConfig`：
`stepInterval = 20`（秒）、`paceInterval = 50`（米）、`poiInterval = 15`（轨迹上传节流秒）、
`validDistance = 25`（打卡半径米）、`sensitiveDistance = 45`、`runFilterAccuracy = 50.0`（精度上限米）、
`gpsFilterAccuracy = 150`（GPS 白名单模式）、`strideStatisticsInterval = 100`。

### 5.2.1 原版记录链路（本项目 `shandong-school_cracked/walker.py` 逐项对齐）

定位回调每 **3000ms** 一次（`LocationComponent` → `lj0.m(context, 3000L, …)`），每次造一个
`RunLatLng` 并进入 `DataComponent.W1()`：

1. 与**上一个有效点**算球面折线距离，`BigDecimal` 四舍五入到整米；
2. 若 `offFenceDisM >= 0` 则扣掉一段（`jLongValue -= offFenceDisM`），负数归零；
3. 过滤 `H0()`：精度超限丢弃（普通 50 米 / 白名单 150 米）；`speed < 0` 且上一点也 `< 0` 丢弃；
   与上一点时间差 > 0 且折算速度 > **10.438 m/s**（≈ 37.6 km/h）丢弃；
4. 通过者 `setValid(true)` 并计入距离，未通过者 `isValid=false`；
5. **无论是否通过都 `i0()` 落库**（所以 `points` 必须有 `is_valid` 列），但只有有效点参与折线累距。

轨迹上传有门限：取 `state in (INIT, FAIL) and isValid=1` 的点，**超过 3 个**才发（`c0()`），
置 `UPLOADING` 按 200 个一批；配速/步频段则**少于 3 段不发**（`b0()` / `d0()`）。
置 `UPLOADING` 按 200 个一批；配速/步频段则**少于 3 段不发**（`b0()` / `d0()`）。打卡点上传
（`uploadPassPoint`）发的是**全量** `targetPoints`（含 `passStatus=false` 的）——原版 `p0()` 传的就是
`getTargetPoints()` 整表，由服务端按 `passStatus` 自行判定，只发已通过的会让服务端看到一份缺项的列表。
时间字段的单位是**跑步内秒**（`Q0() = (currentTime + saveCurrentTime) / 1000`），不是毫秒——
`IntervalStep.setEndTime` 会把 `time = endTime - startTime`，`IntervalPace.setEndDistance` 会把
`distance = endDistance - startDistance`，两者都是原版的联动语义。

只存在本地、**不上传**的字段：`speed`、`isValid`、`isUploaded`、`runCode`（原 App 里标了 `serialize=false`）。
`accuracy` 与 `satellites` **是会上传的**（`RunLatLng` 上没有注解）；`createTime` 也上传，原版在构造器里就赋
`System.currentTimeMillis()`（`RunLatLng.java:199-215`），本项目同样在造点时补齐。

`offFenceDisM` 的语义是「**离开围栏的总距离**」，不是「到围栏边的距离」：原版常态硬编码 `-1`
（`DataComponent.t2()` 直接传 `-1L`），只有「刚回围栏」的那一帧才用 `v2()` 算进出围栏的直线距离，
并 **从 `subDistance` 里扣掉**。本项目围栏外的点整点丢弃（对齐 `SunshineRunService.D()` 的
`if (!K1) return`），所以不会出现进出围栏，`offFenceDisM` 恒为 `-1`。

上传是**分批**的（默认 `DEFAULT_UPLOAD_BATCH=200`）：`uploadRunRecord` 每批成功后服务端按
`indexList` 回执；客户端把状态位从 `STATE_UPLOADING(2)` 改成 `STATE_SUCC(8)` 或 `STATE_FAIL(4)`。

跑步过程中还有**增量上传**：原版 `ApiDataComponent.m0()` 每次定位回调都调，内部按
`CommonConfig.poiInterval`（默认 **15 秒**）节流，达标才把 `state in (INIT, FAIL)` 的待传点发一批。
本项目在 `shandong-school_cracked/walk.py` 的 `_maybe_upload_points()` 里复刻同一套门限：实跑、有 runCode、
`count_points(run_code, INIT) + count_points(run_code, FAIL) > 0`、距上次 ≥ `POI_INTERVAL_S`、且上一轮还没飞完就不重入。
注意门限不能用「尚未落库的点数」——那批点一落库就归零，增量上传会永远不发。

跑步过程中还有**60 秒步频段上传**：原版 `DataComponent.Y1()` 在 `(Q0()-1) % 60 == 0` 时调
`ApiDataComponent.o0()`，后者查未上传步频段、经 `km7.k()` 走 `run/uploadStepsRecord`，并用在途标志防重入。
本项目由 `Walker` 在同样的秒数上置 `step_upload_due`，`walk._maybe_upload_steps()` 消费后异步上传，
失败保留待传（下一分钟再试）。
状态位：`STATE_INIT=1`（待上传）、`STATE_UPLOADING=2`、`STATE_FAIL=4`、`STATE_SUCC=8`。

### 5.3 结算（`run/finishSunRun_v2`）

结算报文就是原版 `DataComponent.t1()`（或 `StopRunUtils.q()`）那一个 Map，键：
`runRecordCode / duration / distance / totalStep / status / stepInterval / paceInterval /
targetPoints / alignType / pauseCount / pauseTimes / sportType`，另外仅在非空时带
`cheatList`、`invalidReasons`。

★ **在此之上还必须带 `runImgRecord` 与 `timestamp` 两个键**：原版 `km7.c()` 在进
`IRunApi.j()`（= `run/finishSunRun_v2`）之前先调 `aw8.c(params)`，该函数无条件塞：

```java
String ts = String.valueOf(System.currentTimeMillis() + r90.D());  // r90.D() 是服务端时间偏移，默认 0
params.put("runImgRecord", HcjNative.encodeRun(runRecordCode, "26101017", "8.7.7", ts, l43.b()));
params.put("timestamp", ts);
```

这条路径不经过 `StopRunUtils.q()`，所以补键发生在 Map 构造之后 —— 只看 `t1()` 会漏掉它们。
算法见 `report/17`（`MD5(code + versionCode + versionName + KEY(env) + ts)`，6/6 预言机验证）。

★ **结算报文里没有 `pois` / `stepList` / `paceList`**（这两个 list 只在**未传完**的续传路径上补）：
轨迹走 `run/uploadRunRecord`、步频走 `run/uploadStepsRecord`、配速走 `run/uploadPaceRecord`、
步幅走 `run/uploadStrideRecord`、打卡点走 `run/uploadPassPoint`，结算只交聚合摘要。
其中 `duration` 是 `String.valueOf(Q0())`（跑步内整秒；`Q0()` 是**墙钟**口径——暂停、原地不动都照走表，配速 = `Q0()` ÷ 公里数，就是原版 `J0()`，所以别用「移动时长」去算配速），`distance` 是 `String.valueOf(S0())`，
`totalStep` 是 `String.valueOf(max(0, L0()))`，`status` = `(cheatType <= 0 && isValid) ? 1 : 0`，
`alignType` 取 `commonConfig.amapGPSLevel`（服务端实测 3，不是写死的）。
`targetPoints` 取 `StartRunEntity.getTargetPoints()` 序列化结果，字段只有
`code / lat / lng / passStatus / clockTime / sort / nfcEnable`。
服务端回 `status`（1 通过 / 0 不通过）与 `invalidReasons`（失效码）。

`pauseCount` / `pauseTimes` 是**实际暂停值**，不是恒 0：原版 `pauseCount` 由 `y0()` 每次暂停 +1，
`pauseTimes = (savePauseTime + pauseTime) / 1000`（秒）；本项目在 `Walker.pause()/resume()` 里累计，结算原样上报。
`cheatList` 本项目不上报——它来自 `SunshineRunService` 里端侧检测 SDK 的回填，服务端仍会自行判定。
### 5.4 客户端本地判定（复刻 `DataComponent.W0`，判定顺序不能换）

| 顺序 | 规则 | 失效码 |
| --- | --- | --- |
| 1 | GPS 有效性（`GPS_STALE_MS=15000`，无定位直接失效） | `25` |
| 2 | 分段步幅异常段数 > `segmentStrideExceptionNum`（仅 `cheatLevel` 为 3/4、且非 `whiteFlag`/`gpsWhiteFlag` 时判，原版 `L1()` 门控；基准用 `segmentStrideAvg`，段距离 ≥ 200 米） | `58` |
| 3 | 距离不在 `[singleMinDistance, singleMaxDistance]`（默认 1000~10000 米） | `2` |
| 4 | 打卡点：`clockMode` 为 2/3 时按 `sort` 顺序逐个命中；为 1 时按 `requiredPointCounts`/`optionalPointGoalCounts`；其余按 `targetPoints` 总数 | `1` |
| 5 | 配速越界（`minPace` 过快 / `maxPace` 过慢） | `3` |

对应实现：`protocol.evaluate_run(...)` → `RunValidity(is_valid, reasons, distance_m, pace_s_per_km,
checkpoints_done, total, status)`，`status` 是 **property**。

## 7. 服务端复核（Mock 里也照做了）

`mock.py` 不只是回 `code:0`，它按规则**真的复核**一遍：距离区间、配速区间、打卡点命中、
